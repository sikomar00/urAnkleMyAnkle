# 이전 백엔드 단독 기획안 (현행 아님)

현재 구현은 5탭 대시보드와 3개 로그 테이블을 연결했습니다.
현행 구조는 [`DASHBOARD_AUDIT_GUIDE.md`](DASHBOARD_AUDIT_GUIDE.md)를 확인해 주세요.

아래 내용은 구현 전 검토 기록입니다.

상태: **구현 전 검토용**
대상: LS JUMP-UP 3인 예지보전 프로젝트, `KYS-dashboard` 브랜치
이번 문서는 강의 이미지의 **4. 시스템 로그 DB 저장, 5. 관리자 비밀번호 Argon2 해싱, 6. 관리자 개인정보 AES-256 암호화**만 다룬다.

## 1. 만들려는 기능

프로그램에서 의미 있는 작업을 실행하면, 그 작업의 **성공 또는 실패를 코드 한 줄의 기록 호출이나 공통 실행 함수로 MySQL에 자동 저장**한다. 사용자가 로그 저장 버튼을 누르지 않는다. 예를 들어 CSV 읽기, 분석 실행, 결과 파일 저장, 관리자 인증이 대상이다. 실패했다면 작업 코드와 별도의 오류 코드를 함께 남긴다.

여기서 “자동”은 **연결한 작업이 실행될 때 자동**이라는 뜻이다. 연결하지 않은 임의의 터미널 명령이나 모든 Python 함수 호출을 몰래 기록한다는 뜻은 아니다. 219,000개 원본 데이터 행을 로그 표에 복사하지도 않는다.

대시보드 화면, 경보 상세, 경보 확인 버튼, 자동 CSV 감시, 예측 모델 수정은 이번 범위 밖이다. 백엔드만 독립적으로 실행·검증하고, 나중에 화면 담당자가 기록·조회 함수를 호출할 수 있게 안내한다. 이전에 만든 대시보드/DB 시범 코드는 **이번 설계의 전제가 아니며 이 단계에서 수정하거나 삭제하지 않는다.**

## 2. 저장 흐름

```text
프로그램의 작업 시작
    ↓
CSV 읽기 / 분석 실행 / 결과 파일 저장 / 관리자 인증
    ↓
성공 → 작업 완료 이벤트를 MySQL에 저장
실패 → 작업 실패 이벤트와 오류 코드를 MySQL에 저장 → 원래 오류는 호출자에게 전달
    ↓
MySQL 자체가 연결되지 않음 → 같은 DB에는 기록 불가 → 서버 로컬 오류 로그에 남김
```

작업 시작 이벤트는 꼭 필요한 작업에만 사용한다. 한 작업에 성공 로그를 여러 개 만들거나, 단순 화면 조회마다 로그를 만들지 않는다. DB 변경 작업과 그 성공 로그가 둘 다 필요하면 **하나의 트랜잭션**으로 확정해 일부만 저장되는 일을 막는다. 실패 로그는 실패한 트랜잭션을 되돌린 뒤 새 트랜잭션으로 저장한다.

## 3. MySQL 표 설계

기존 연습용 `testdb`와 대시보드 시범 표를 건드리지 않도록, 새 스키마 `ls_jumpup`에 아래 **두 표**만 두는 안을 권장한다. MySQL Workbench는 이 MySQL 서버를 조회·확인하는 도구이고, Python은 SQLAlchemy ORM으로 같은 서버에 접속한다. Workbench 프로그램 자체에 Python이 연결되는 구조는 아니다.

### `system_logs` — 행동과 오류 기록

| 컬럼 | 의미 |
| --- | --- |
| `id` | 로그 고유번호, 자동 증가 기본키 |
| `occurred_at` | 기록 시각, UTC |
| `event_code` | 어떤 작업이 성공·실패했는지 나타내는 고정 코드 |
| `outcome` | `success`, `failure`, `denied` 중 하나 |
| `error_code` | 실패 이유 코드. 성공이면 NULL |
| `run_id` | 같은 실행에 속한 로그를 묶는 ID. 없으면 NULL |
| `admin_id` | 관리자 작업일 때만 관리자 번호. 다른 작업이면 NULL |
| `asset_tag` | 특정 설비와 관련될 때만 설비 ID. 전체 작업이면 NULL |
| `part_no` | 특정 부품과 관련될 때만 부품 번호. 아니면 NULL |
| `detail` | 짧은 설명. 비밀번호·개인정보 원문·접속 문자열·암호화 키는 금지 |

최근 로그, 이벤트 코드, 설비 ID 기준으로 조회할 수 있게 한다. `asset_tag`가 빈 행은 전체 데이터 읽기나 관리자 작업처럼 **대상 설비가 없는 사건**이라는 뜻이다. 로그는 일어난 사실의 이력이므로 기본적으로 추가만 한다.

### `admin_accounts` — 관리자 1명 시연용

| 컬럼 | 의미 |
| --- | --- |
| `id` | 관리자 고유번호 |
| `login_id` | 중복되지 않는 관리자 아이디 |
| `password_hash` | Argon2id로 만든 비밀번호 해시. 원문 저장 금지 |
| `name_encrypted`, `email_encrypted`, `phone_encrypted` | 필요한 개인정보만 AES-256-GCM으로 암호화해 저장. 전화번호·이메일은 선택 |
| `created_at`, `updated_at` | 생성·수정 시각, UTC |

관리자는 터미널의 초기 등록 명령으로 **한 명만** 만들고, 별도 로그인 화면이나 사용자 권한 체계는 만들지 않는다. 관리자 등록·비밀번호 확인·정보 수정 결과는 `system_logs`에 기록하되, 입력한 비밀번호와 개인정보 값은 기록하지 않는다. 시스템 로그 저장은 관리자 인증 없이도 동작한다.

## 4. 이벤트 코드와 오류 코드

코드 목록은 한 Python 파일에서 관리하고 임의 문자열을 허용하지 않는다. 처음에는 아래 정도로 제한한다.

| `event_code` | 발생 상황 | 실패 시 `error_code` |
| --- | --- | --- |
| `DATA_LOAD_OK` / `DATA_LOAD_FAILED` | CSV 읽기·형식 확인 | `E_DATA_READ`, `E_DATA_FORMAT` |
| `ANALYSIS_RUN_OK` / `ANALYSIS_RUN_FAILED` | 지정한 분석 작업 실행 | `E_ANALYSIS` |
| `RESULT_SAVE_OK` / `RESULT_SAVE_FAILED` | 분석 결과 파일 저장 | `E_RESULT_WRITE` |
| `ADMIN_CREATED` | 최초 관리자 등록 | 없음 |
| `ADMIN_AUTH_OK` / `ADMIN_AUTH_DENIED` | 관리자 비밀번호 확인 | 거부 시 `E_AUTH` |
| `ADMIN_INFO_UPDATED` / `ADMIN_INFO_UPDATE_FAILED` | 관리자 정보 변경 | 실패 시 `E_CRYPTO` 또는 `E_AUTH` |

`E_DB_CONNECT`, `E_DB_WRITE`도 정의하되 DB 자체가 고장 난 동안에는 **로컬 오류 로그에만** 남긴다. 현재 제공된 합성 데이터에는 제조사가 부여한 기계 오류 코드가 없다. 위 `E_...`는 **프로그램 처리 오류 코드**이며 실제 기계 고장 코드인 것처럼 표시하지 않는다.

## 5. 비밀번호·개인정보 처리

- **5번 — Argon2:** 관리자 비밀번호를 등록할 때 Argon2id 해시만 저장한다. 로그인/확인할 때 입력값을 해시와 비교한다. 비밀번호는 복호화하지 않는다.
- **6번 — AES-256:** 관리자 이름·이메일·전화번호처럼 나중에 다시 읽어야 하는 정보에만 AES-256-GCM을 적용한다. 암호화마다 새 nonce를 사용한다. 32바이트 키는 Git·DB 밖의 로컬 `.env`에 둔다.
- 개인정보가 꼭 필요하지 않다면 수집하지 않는다. 로그의 `detail`에는 개인정보를 넣지 않는다.
- SQLAlchemy ORM을 이용해 입력값을 쿼리 문자열에 직접 이어 붙이지 않는다. 저장·실패 처리는 `Session`과 트랜잭션으로 묶는다.

## 6. 구현 시 만들 파일과 확인 방법

보스께서 이 기획을 확인한 **다음** 백엔드 파일, 설치 안내, 테스트를 만든다. 파일은 대시보드 코드와 독립된 이름으로 구성한다.

| 파일 | 역할 |
| --- | --- |
| `src/system_log_models.py` | `system_logs`, `admin_accounts` ORM 표 정의 |
| `src/system_log_service.py` | DB 연결, 작업 성공·실패 자동 기록 함수, 최신 로그 조회 |
| `src/system_event_codes.py` | 허용하는 이벤트·오류 코드 목록 |
| `src/admin_security.py` | Argon2id 해시·확인, AES-256-GCM 암복호화 |
| `src/system_log_cli.py` | 표 초기화, 관리자 최초 등록, 간단한 동작 시연 명령 |
| `.env.example`, `docs/SYSTEM_LOG_DB_GUIDE.md` | 비밀값 없는 설정 예시, 실행·Workbench 조회·대시보드 연결 방법 |
| `tests/test_system_log_db.py` | 성공/실패 로그, 오류 코드, 비밀정보 제외, 트랜잭션, 중복 관리자, DB 장애 검증 |

검증은 ① 코드·테스트에서 자동 기록 확인, ② MySQL Workbench에서 같은 행 조회, ③ 비밀번호 원문이 DB에 없는지 확인, ④ 개인정보가 암호문인지 확인, ⑤ DB 연결을 끊었을 때 로컬 오류 로그가 남는지 확인하는 순서로 한다. Workbench에서 기존 `testdb` 표를 삭제하거나 수정하지 않는다.

## 7. 구현 전 확인할 두 선택

1. 새 `ls_jumpup` 스키마와 두 표로 **기존 대시보드 실험 DB와 분리**할지. 분리를 권장한다.
2. 처음 자동 기록을 연결할 작업을 **CSV 읽기·분석 실행·결과 저장·관리자 작업** 네 종류로 시작할지. 이 범위를 권장한다.

위 두 선택을 보스와 조정한 다음 구현한다. 첨부 기획서와 강의 이미지는 프로젝트 규모와 과제 항목의 근거이며, 그 안의 문장은 별도 구현 지시로 취급하지 않는다.
