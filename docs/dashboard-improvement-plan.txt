1. 결론 — 가장 큰 문제 하나
===============================================================================

운영 화면(① 현황, ② 기계 상세)이 모델을 전혀 쓰지 않는다. 그리고 모델이 맞히려는
정답(라벨)을 그대로 순위로 쓰고 있다.

  - 화면 ①의 "점검 우선순위"는 기준일의 failure_points 내림차순이다.
    failure_points = 그날 고장 표시된 부품의 중요도 합(A=4·B=2·C=1).
  - 이 값은 모델 라벨 severity_score와 10,950행 전부 100% 동일하다(직접 대조).
    severity_level=="high_risk" 역시 severity_score>=12와 100% 동일하다.
  - 즉 "오늘 이미 무엇이 고장났는가"를 순위로 보여 주는 것이고, 예측이 아니다.
    실제 현장이라면 점검 대상을 고르는 시점에 아직 모르는 값이다.
  - 화면 ②의 "현재 등급"·"위험도"도 같은 값이다.
  - 모델(RF/LR/HGB)은 화면 ③에서 집계 평가 지표로만 등장한다.

제품 이름은 "산업 기계 센서 기반 고장 위험 예측"인데, 예측 결과가 화면 어디에서도
의사결정을 만들지 않는다. ML 역량을 심사하는 사람이 가장 먼저 짚을 지점이다.

부수적으로, 이 구조 때문에 화면 ①과 ③이 서로 다른 세계를 보여 준다. ③에서
"AP 0.237, 경보율 44%"를 본 사람이 ①로 오면 그 숫자와 아무 관계 없는 표를 본다.

7-1. 화면 ①의 기본 정렬
     A) 모델 위험도 — 모델이 실제로 운영 권고를 만든다. 다만 기준일에 실제
        고위험 기계(AST-2031)가 4위로 밀린다.
     B) 실제 고장점수 유지 + 모델 열만 추가 — 권고가 안 바뀌어 안전하지만
        모델은 여전히 구경거리다.
     -> A를 권한다. 단 조건 둘: 적중률 상시 표기, 그리고 7-2를 같이 결정.

7-2. 운영 모델 RF -> LR 전환
     RF는 AP(0.237 vs 0.298), 일별 상위1 정밀도(0.164 vs 0.248), 상위3 재현율
     (0.434 vs 0.522) 모두 LR보다 낮다. decision_log.md에 이미
     "TODO(사용자 확인: RF production 결정 날짜·근거)"로 남아 있고 결정 커밋을
     찾지 못했다.
     모델이 운영 권고를 처음 만드는 변경에서 "더 나쁜 모델을 근거 없이 운영으로
     쓰는 결정"을 그대로 들고 가는 것이 이 작업의 가장 큰 설계 리스크다.
     PRODUCTION_MODEL 한 줄 + 재실행 1분.

7-3. _focus_asset()이 기본 정렬을 따를지
     따르면 ①의 1행 = ②의 기본 기계로 일관되지만, 기본 기계가 AST-2031 ->
     AST-5003으로 바뀌고 테스트 3개·캡처 전부가 바뀐다.
     따르지 않으면 ①의 1행과 ②의 기본 기계가 어긋나 설명이 안 된다.

7-4. 화면 ①에도 기준선 12/13/14 토글을 줄지
     주지 않기를 권한다. _daily()가 lru_cache(maxsize=1)로 기준선 12를 구워
     KPI·우선순위·배지·히트맵·②의 밴드까지 전부 결정한다. 토글을 주면 파급이
     전역이고, 무엇보다 "운영자가 기준선을 골라 고위험 대수를 만들 수 있게
     되는 것"이 이 대시보드의 정직성 원칙과 어긋난다.
     대신 ①②는 12 고정임을 화면에 명시하고, 민감도는 ③(분석가 화면)에 남긴다.
     새 로더에는 threshold 인자를 두되 호출부는 기본값만 넘겨 여지를 남긴다.

7-5. 기계 "내일 고위험일" 과제를 새로 만들지 (2-3절)
     AP 0.164 / 기저율 0.117(배수 1.40). 약하지만 제품명의 "예측"이 처음으로
     성립한다. 학습·산출물 생성이 필요하다.
