# 산업 장비 데이터 Feature 설명

작성 기준: 2026-09-22의 `src/industrial_features.py`.
이 문서는 공통 학습 코드의 실제 입력을 설명합니다. 별도로 실험 중인 EDA·랜덤 포레스트 코드의 `feature_data`는 다를 수 있습니다.

## 1. Feature와 Target

- **Feature(X)**: 모델이 판단할 때 참고하는 입력 정보입니다.
- **Target(y)**: 모델이 맞혀야 하는 정답입니다.
- 현재 상태 분류의 정답은 `breakdown_flag`입니다. 이 컬럼을 입력에도 넣으면 정답 누수가 발생합니다.
- 물리적으로 고장과 관련 있는 변수라도 이 데이터에서 정상과 고장을 구분하는 정보가 충분하다는 뜻은 아닙니다.

## 2. 현재 상태 모델의 입력 9개

아래 의미와 단위는 컬럼명에 따른 해석입니다. 정확한 측정 위치·주기·집계 방식은 원본 데이터 설명으로 확인해야 합니다. 고장과의 관계는 검토할 가설이며, 이 데이터에서 검증된 인과관계가 아닙니다.

| Feature | 의미·단위 | 모델에서 기대하는 역할 | 확인할 점 |
|---|---|---|---|
| `machine_type` | 기계 유형, 범주형 | 기계마다 다른 운전 조건을 구분 | 같은 온도·진동도 기계 유형에 따라 의미가 다를 수 있음. CNC만 분석하면 상수이므로 그룹 내부 구분 정보는 없음 |
| `temp_bearing_degC` | 베어링 온도, °C | 베어링의 열 상태 반영 | 정상·고장의 분포 차이, 부하와 RPM에 따른 차이 |
| `temp_motor_degC` | 모터 온도, °C | 모터의 열 상태 반영 | 높은 부하로 인한 상승과 이상 과열을 구분할 정보가 있는지 |
| `vibration_h_mms` | 수평 방향 진동 속도, mm/s | 진동 상태 반영 | RPM·부하·기계 유형을 함께 고려해도 고장과 관계가 있는지 |
| `vibration_v_mms` | 수직 방향 진동 속도, mm/s | 다른 방향의 진동 상태 반영 | 수평 진동과 중복되는지, 추가 정보를 주는지 |
| `oil_pressure_bar` | 오일 압력, bar | 윤활·유압 계통 운전 상태의 단서 | 기계별 정상 범위와 압력 이상 여부. 모든 기계에서 같은 의미라고 가정하지 않기 |
| `load_pct` | 부하율, % | 온도·진동·전력의 변화가 운전 조건 때문인지 설명 | 부하가 높을 때와 낮을 때 센서값·고장 비율 비교 |
| `shaft_rpm` | 축 회전 속도, rpm | 진동·전력 등을 해석하는 운전 조건 | 값이 거의 일정한지, 부하·진동과 함께 유용한지. 단순 상관이 낮다는 이유만으로 제거하지 않기 |
| `power_consumption_kw` | 전력 관련 값, kW | 다른 운전 조건 대비 전력 변화의 단서 | kW는 전력이며 에너지 사용량인 kWh와 다름. 부하·RPM을 고려한 비교 필요 |

현재 코드의 입력 목록은 다음과 같습니다.

```python
feature_data = [
    "machine_type",
    "temp_bearing_degC",
    "temp_motor_degC",
    "vibration_h_mms",
    "vibration_v_mms",
    "oil_pressure_bar",
    "load_pct",
    "shaft_rpm",
    "power_consumption_kw",
]
target_data = "breakdown_flag"
```

## 3. 식별·날짜·정답 컬럼의 역할

데이터에 존재하는 컬럼이 모두 모델 입력은 아닙니다.

| 컬럼 | 의미 | 현재 상태 모델 | 미래 예측 모델 |
|---|---|---|---|
| `transaction_date` | 기록 날짜 | 날짜 분할에 사용, 원본 날짜는 입력 아님 | 정렬·과거 변수·날짜 변수 생성에 사용 |
| `asset_tag` | 개별 장비 식별자 | 장비별 분석 그룹 구분, 입력 아님 | 장비·부품별 이력 계산과 분석 그룹 구분, 입력 아님 |
| `part_no` | 부품 번호·식별 정보 | 입력 아님 | 입력 및 이력 계산 그룹에 사용 |
| `plant_code` | 공장 코드 | 입력 아님 | 입력에 사용 |
| `breakdown_flag` | 해당 행의 고장 여부, 0/1 | 정답. 입력 금지 | 미래 정답·과거 고장 이력 생성에 사용. 원본 값은 입력 아님 |
| `label_end_date` | 정답을 관측하는 구간의 마지막 날짜 | 해당 날짜로 설정 | 미래 정답 기간의 끝. 날짜 분할 시 누수 방지에 사용, 입력 아님 |

`machine_type`은 기계 종류, `asset_tag`는 개별 장비, `part_no`는 부품 식별 정보입니다. `part_no`가 공통 부품 종류인지 개별 부품의 고유 번호인지는 별도로 확인해야 합니다. 식별자를 추가한다고 항상 성능이 좋아지는 것은 아니며, 기존 장비·부품을 기억하는 효과와 새로운 대상에 일반화하는 능력을 구분해야 합니다.

## 4. 미래 고장 모델의 입력 40개

기본 정답 `target_7d`는 같은 장비·부품에서 **다음 날부터 7일 동안 한 번이라도 고장이 있으면 1**, 없으면 0입니다. 미래 7일의 날짜가 모두 관측되지 않으면 학습 대상에서 제외합니다. 현재 이미 고장으로 표시된 행도 예측 대상에서 제외합니다.

| 입력 종류 | 개수 | 코드에서 계산하는 내용 |
|---|---:|---|
| `machine_type`, `part_no`, `plant_code` | 3 | 기계·부품·공장 정보 |
| 센서별 `_lag1` | 8 | 같은 장비·부품의 이전 1행 값 |
| 센서별 `_lag3` | 8 | 이전 3행 값 |
| 센서별 `_lag7` | 8 | 이전 7행 값 |
| 센서별 `_mean7` | 8 | 현재 행을 제외한 이전 최대 7행 평균. 유효값 3개 이상일 때 계산 |
| `breakdown_lag1` | 1 | 이전 1행의 고장 여부 |
| `breakdown_count_30d` | 1 | 현재 행을 제외한 이전 최대 30행의 고장 표시 합. 최소 1개 유효값 필요 |
| `day_of_week` | 1 | 요일: 월요일 0부터 일요일 6 |
| `month_sin`, `month_cos` | 2 | 월을 주기적인 값으로 표현해 연말·연초의 연결을 반영 |

예: `shaft_rpm_lag1`은 과거 RPM, `vibration_h_mms_mean7`은 과거 수평 진동의 이동평균입니다. 원본 센서 8개 자체는 현재 미래 모델의 입력 목록에 포함되지 않습니다.

**주의:** 현재 구현의 `shift`와 `rolling`은 날짜가 아니라 행 기준입니다. 장비·부품마다 하루 한 행이 연속으로 있어야 이전 7행이 7일과 같습니다. `breakdown_count_30d`도 실제로는 이전 30행의 합이며, 서로 다른 고장 사건의 횟수를 직접 세는 것은 아닙니다. 과거 고장 기록을 쓰려면 예측 당시 그 기록을 실제로 알 수 있어야 합니다.

## 5. Feature가 부족할 수 있는 상황

코드는 장비·부품·날짜별 행을 다룹니다. 같은 장비·날짜의 센서값이 같더라도 부품별 고장 여부는 다를 수 있습니다.

| 온도 | 진동 | 부품 | 고장 여부 |
|---:|---:|---|---:|
| 80 | 3.2 | A | 0 |
| 80 | 3.2 | B | 1 |

온도와 진동만 입력하면 두 행은 모델에 동일하게 보입니다. 이런 입력으로 개별 행의 정답을 완벽히 구분할 수는 없습니다. 부품 정보·이력 등 추가 정보가 도움이 되는지 검증해야 합니다. 이 현상이 현재 낮은 성능의 원인이라고 확정된 것은 아닙니다.

## 6. 무엇을 확인하고 개선할까?

1. **정상·고장 분포 비교:** 기계 유형·부품별로 센서의 박스플롯과 분포를 비교합니다. 평균만 같거나 상관계수가 낮다는 이유로 쓸모없다고 결론 내리지 않습니다.
2. **동일 입력의 정답 충돌:** 같은 feature 조합에 0과 1이 얼마나 섞이는지 확인합니다.
3. **정보가 거의 없는 변수 확인:** 특정 그룹에서 값이 고정되거나 결측이 많은지 확인합니다.
4. **시간 정보 추가 실험:** 미래 예측에는 변화량, 과거 표준편차, 부품별 이력 등을 후보로 검토합니다. 추가하면 반드시 좋아지는 것은 아닙니다.
5. **변수 포함·제외 비교:** 같은 날짜 분할에서 RPM 등을 넣고 뺀 모델을 비교합니다. 가능하면 상관된 변수 묶음의 영향도 함께 봅니다.
6. **검증 데이터에서 선택:** 전처리는 학습 데이터로만 맞추고, feature·가중치·판단 기준은 검증 데이터에서 선택합니다. 테스트는 마지막 평가에 사용합니다.

`breakdown_flag`, 미래 정답, 예측 시점 이후에 기록되는 정비 정보 등을 입력으로 사용하면 성능이 부풀려질 수 있습니다. 높은 Accuracy만으로 성공을 판단하지 말고 Precision·Recall·F1과 오경보·놓친 고장 건수를 함께 확인합니다.

현재 낮은 지표만으로 특정 feature가 잘못됐다고 확정할 수는 없습니다. 모델 크기를 늘리기 전에 입력이 실제 정답을 구분하는 정보를 제공하는지 확인하는 것이 목적입니다.
